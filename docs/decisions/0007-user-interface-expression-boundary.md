# ADR-0007：普通用户界面不暴露内部治理与运行机制

- **状态**：Accepted，已实现首轮收敛
- **决策日期**：2026-08-09
- **适用范围**：登录、画像、书架、教材生成、阅读、验证、笔记、Ask Me 与错误提示
- **关联决策**：[ADR-0001](0001-lesson-generation-v2.md)、[ADR-0003](0003-modular-monolith-boundaries.md)、[ADR-0006](0006-daily-mode.md)

## 1. 问题

Slow 需要严谨的生成治理、版本留痕和学习证据边界，但这些内部机制曾被直接写进普通用户界面，例如 `Learning Contract`、发布门禁、生成轮次、观察水位、原始任务状态、模型理由和掌握概率。

这些信息对开发者审计有价值，却不能帮助学习者判断当前状态或完成下一步。直接展示还会带来三类风险：

1. 用户必须理解实现架构才能使用产品；
2. 内部字段或模型原文被误当作产品承诺；
3. “已通过结构校验”等表述被误解为事实已经核验。

## 2. 决策

普通用户界面只回答三个问题：

1. 现在是什么状态；
2. 这会怎样影响用户；
3. 用户下一步能做什么。

内部治理与运行数据继续完整保存，但只能出现在开发者工具、受控日志或专用审计界面。普通用户界面不得直接展示：

- `Learning Contract`、稳定 ID、内容版本 ID 和内部任务名；
- 生成或修复轮次、尝试次数、发布门禁和原始状态枚举；
- 观察水位、投影算法、原始掌握概率和证据内部分类；
- 模型或服务端返回的原始 `rationale`、错误详情、堆栈和错误码；
- 会暴露系统编排方式、但不改变用户决策的实现说明。

前端必须通过显式映射把内部状态转换为经过设计的用户文案。不得把服务端对象字段直接插入普通用户页面作为说明文字。

### 2.1 同一结果只保留一个主状态表达

同一用户结果在同一视图中只能有一个主状态区。父流程、后台子任务和操作按钮不得分别重复说明同一件事：

- “评分已保存、笔记准备中、下一节准备中”应合并为一条面向学习结果的状态，而不是连续堆叠通知和任务卡；
- 等待期间只说明正在发生什么及其影响，不用不可操作的禁用按钮再次复述“准备中”；
- 只有操作真正可执行时才显示入口，只有失败需要用户介入时才显示恢复动作；
- 子任务名、尝试次数和重试编排默认留在审计层。部分失败时，只说明受影响的用户成果以及是否妨碍继续学习。

这条约束不要求隐藏并行任务的真实失败；它要求界面从用户决策出发，将多个内部状态归并为一个可理解、可操作的产品状态。

## 3. 必须保留的透明度

收起内部机制不等于隐藏重要事实。以下信息必须用普通语言明确说明：

- 内容是 AI 生成、授权内容、历史内容还是 Demo 内容；
- 发布检查不等于逐项事实核验，关键事实应结合参考来源判断；
- 某项操作是否影响学习进度、解锁、已有成绩或后续教材；
- 数据的账号归属、隐私用途、删除影响和预计处理时限；
- 错误发生后用户可以等待、重试、刷新还是联系支持。

界面不得暗示系统完成了实际没有完成的事实核验、人工审核、安全保证或删除动作。

## 4. 错误与原始响应边界

用户侧错误必须说明可理解的结果和恢复动作。API 的公开 `message` 可以作为经过设计的用户提示；原始 `error`、错误码、操作 ID、任务详情、重试计数和流式异常内容不得直接展示。

模型 `rationale` 只作为内部候选或审计材料。系列卡片、重规划确认和其他高频入口必须使用产品定义的摘要，不能把 `rationale` 当作文案字段。

## 5. 不变的服务端约束

本决策只改变展示边界，不改变任何服务端权威：

- Learning Contract 与稳定目标 ID 继续约束正文和测验；
- 结构校验、失败关闭、原子发布和版本留痕继续执行；
- 解锁、评分和掌握度仍由服务端计算；
- Demo、真实内容与失败候选继续机器可识别并保持隔离；
- 完整运行血缘继续可供开发者审计。

不得以“简化文案”为理由降低校验门槛、吞掉失败、伪造成功或删除审计数据。

## 6. 首轮实现与验收

首轮收敛覆盖登录与隐私、学习画像、书架与系列卡片、下一本书确认、生成进度、正文可信提示、Fast View、验证门禁、后续任务、学习笔记、掌握状态和 Ask Me。

最低验收条件：

- 普通用户组件中不再出现本 ADR 禁止的关键内部术语或原始字段；
- 同一结果不会由成功提示、准备提示、任务卡和禁用按钮重复表达；
- AI、Demo、事实检查边界、隐私和删除时限仍有清晰提示；
- TypeScript 检查与生产构建通过；
- 后续新增用户文案在评审中同时检查“影响、下一步、是否误导”三项。
